# S1 walkthrough: multi-user agent loop + raw log

S1 builds the base everything else stands on. Users talk to an agent through a CLI. The agent can search the web, fetch pages, and read and write files in its own workspace. Every event is stored per user in an append-only log, and there is **no memory**: a new session starts blank.

## Suggested reading order

Read bottom-up: data first, then the rules around it, then the loop, then the edges.

1. `migrations/versions/0001_s1_initial.py`: the four tables, the append-only trigger, and `redact_event`. Everything else exists to write into these tables correctly.
2. `memagent/sanitize.py`: the scrubbing gateway. Note the rule order and the check-digit helpers.
3. `memagent/store.py`: the only module that touches the database. Every function takes `user_id`. Read `append_event` and `session_lock` carefully.
4. `memagent/llm/types.py` → `base.py` → `fake.py` → `openai_provider.py`: our own message types, the interface, the scripted fake, and the one file that knows OpenAI's format.
5. `memagent/pricing.py` + `config/prices.toml`: how `cost_usd` is computed.
6. `memagent/tools/base.py`: the tool protocol and the registry that never raises. Then the tools themselves: `workspace.py`, `web_fetch.py` (+ `html_text.py`), `web_search.py`.
7. `memagent/agent/history.py` → `loop.py`: events back into messages, and the loop itself.
8. `memagent/api/` (`app.py` → `deps.py` → `routes.py`) and `memagent/cli.py`: the edges.
9. `tests/`: start with `test_agent_loop.py` and `test_append_only.py`.

## One message, end to end

A user types `what's new in Postgres 17? save a summary to notes.md` into `memagent chat`.

**CLI** (`cli.py::chat`)
1. When chat started, it called `POST /sessions` with `Authorization: Bearer mk_…` and got a new session id.
2. Now it sends `POST /sessions/{id}/messages {"text": "..."}` over HTTP, the same way any other client would.

**API** (`api/deps.py`, `api/routes.py::post_message`)
3. `current_user` hashes the bearer key with SHA-256 and looks up `users.api_key_hash`. No match gives 401.
4. `_own_session_or_404` runs `store.get_session(db, user.id, session_id)`, which filters by **both** id and user_id. Someone else's session gives 404, the same answer as a missing one.
5. The request's read transaction is committed so its connection isn't held for the whole turn. Then it calls `agent.loop.run_turn(deps, user.id, session_id, text)`.

**Agent loop** (`agent/loop.py`)
6. `store.session_lock` takes `pg_advisory_lock(key(session_id))` on a dedicated connection. A concurrent request for the same session waits here.
7. `store.append_event(..., "user_message", {"text": ...})` scrubs the payload (`sanitize.scrub_json`), computes `seq = max(seq) + 1`, inserts, and commits. This is seq 1, for example.
8. **Step 1**: `_call_model` reads all events back with `store.list_events` and turns them into messages (`history.events_to_messages`), with the system prompt first. The model therefore sees only what was persisted, already scrubbed.
9. `llm.complete(messages, tools.specs(), AGENT_MODEL)`. In production that's `OpenAIResponsesClient`: `to_responses_input` converts our messages to Responses API items, the request goes out with `store=False`, and `from_responses_output` converts the reply back into an `LLMResponse`.
10. `cost_usd(prices, AGENT_MODEL, usage)` → `store.record_llm_call(module="agent", …)`. That is one `llm_calls` row per model call.
11. The model asked for `web_search({"query": "Postgres 17 new features"})`. The loop appends a `tool_call` event, then `ToolRegistry.execute` runs `WebSearchTool.run`:
    - `OpenAISearchProvider.search` makes a **separate** Responses request with `SEARCH_MODEL`, `tools=[{"type": "web_search"}]` and `max_tool_calls=1`. It counts the `web_search_call` items, parses the JSON results, and drops any URL the search didn't actually return.
    - It writes its own `llm_calls` row with `module="search"` and `search_calls=1`.
    - It returns a numbered title/URL/snippet list.
12. The loop appends a `tool_result` event. That event is scrubbed too, because web content can contain anything.
13. **Step 2**: history is rebuilt again (now including the call and its result), and the model is called again. It asks for `workspace_write({"path": "notes.md", "content": "..."})`.
14. `WorkspaceWriteTool` resolves `data/workspaces/<user_id>/notes.md`, checks that it is still inside that root, scrubs the content, checks the size limit, writes the file, and returns `wrote N bytes`. The loop records `tool_call` + `tool_result`.
15. **Step 3**: the model answers with text and no tool calls. The loop appends an `assistant_message`, returns `TurnResult(reply, steps, cost_usd)`, and the lock is released.

**Back out**
16. The route returns `{"reply": ..., "steps": [{"tool": "web_search", ...}, {"tool": "workspace_write", ...}], "cost_usd": ..., "stopped_by_limit": false}`.
17. The CLI prints each tool step, the reply, and the turn's cost.

That one turn produced 7 events (`user_message`, 2 × `tool_call`/`tool_result`, `assistant_message`) and 4 `llm_calls` rows (3 agent + 1 search).

## Why it is built this way

| Choice | Reason | Record |
|---|---|---|
| Hand-written loop | Every step must be persisted, scrubbed, locked and priced our way. Frameworks own their state. The whole flow fits on one screen. | 0001 |
| Append-only `events`, trigger-enforced | All later memory derives from this log. The rule must hold for every client, including `psql`. Redaction is the one, narrowly shaped exception. | 0002 |
| Scrub before persisting, history rebuilt from the DB | A secret on disk is leaked forever. One gateway is auditable. The model sees only scrubbed text, at the cost that tasks needing real secrets are impossible. | 0003 |
| SHA-256 API keys | Keys are 256-bit random values, so slow hashing adds nothing. A deterministic hash allows an indexed lookup. | 0004 |
| `web_search` wraps hosted search | Caps and counts searches, logs results as normal tool results, prices search separately, keeps the agent provider-neutral. | 0005 |
| Session-level advisory lock | Serializes turns across processes without a long transaction. Events commit one by one. Postgres releases the lock if the process dies. | 0006 |
| Composite FKs `(session_id, user_id)` | The database itself refuses an event or `llm_calls` row that names another user's session. Multi-tenancy doesn't rest on application code alone. | n/a |
| A step is one model call. At the limit, tool calls are dropped and an `error` event is written | A stored tool call without a result would make every later request in the session invalid. `error` events are skipped when rebuilding history. | n/a |
| Price by the configured model name | The API may report a dated snapshot name that isn't a key in the price table. A missing price fails at startup, before any spend. | n/a |
| `store=False`, no reasoning items replayed | Our database is the single history. OpenAI-side state would be a second, unscrubbed copy. The cost is that a reasoning model re-derives its reasoning between steps. | n/a |
| Logs carry no user content | Tool crashes log only the exception class, because messages and tracebacks can echo user input. | n/a |

## Known gaps (deliberate in S1)

- **DNS rebinding in `web_fetch`.** We resolve and check every address, on every redirect hop, but httpx resolves the name again when it connects. A malicious DNS server could answer differently the second time. The fix is a transport pinned to the checked IP.
- **The append-only trigger checks the shape of an UPDATE, not who made it.** Limiting redaction to `redact_event` alone needs DB roles (S7).
- **No lock-wait timeout.** A second request waits for as long as the first turn takes.
- **Tools run sequentially, with no streaming.**
- **`redact_event` exists and is tested, but nothing calls it yet.** It gets wired into "forget" in S7.
